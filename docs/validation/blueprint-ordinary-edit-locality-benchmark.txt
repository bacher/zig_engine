Ordinary completed-edit locality benchmark
Date: 2026-11-08
Baseline: c0ecb6c584802fac7e4c545e44fc5dd163c3e964
Fixed: the working-tree pendingTargetsMayAffectEdit early exit in world.zig
Host: the same native arm64 macOS machine; Zig 0.16.0, ReleaseFast

Reproduce the maintained fixture:
  zig build bench-placement -Doptimize=ReleaseFast
The existing placement benchmark calls ordinary_edit_benchmark.run(init).
For a baseline run, apply only the benchmark source and its one main-call line
to c0ecb6c; retain that commit's world.zig. No new build target is required.

Methodology
-----------
The synthetic resident reader supplies a 3x3x3 stone foundation, four vertical
planks, and one side plank. The same reader and five constructed cells feed:
  physical: validateEdit directly;
  no_site: validateCompletedEdit with an empty blueprint State;
  distant_site: validateCompletedEdit with one pending plank at (160,160,10).
The world is 8x8x8 chunks (256x256x256 blocks), with periodic X. The distant
target cannot affect the edit's support-radius-28 cube. The ordinary additions,
rejected support removal, accepted side-plank removal, and already-exists case
all compare their complete EditResult with direct physical validation.

Each row first counts physical reads, allocation calls and requested allocation
bytes, and verifies that all validation storage is freed. These counts are
deterministic for this fixture. The captured temporary harness used a transparent
allocator wrapper; the maintained source uses std.testing.FailingAllocator with
failures disabled. Both delegate to init.gpa, and timed loops use init.gpa
directly. Setup and publication finish before measuring.

Each path warms up for 100 checks, then records 11 samples of 1000 checks. Rows
report the sample median and minimum in microseconds per check. One complete
baseline and fixed binary run was discarded to warm the machine, followed by
three interleaved baseline/fixed process pairs. Both preserved binaries were
compiled from the same temporary harness before these pairs were run. No builds
ran concurrently with the measurements. The raw paired outputs follow below.

These are detached validation timings. They exclude chunk collection, preview
cache handling, roads, service commits, rendering and storage. Reader callbacks
also count accesses during timing, equally in all paths. Wall times describe
this fixture and machine; read and allocation counts are the stronger evidence.

Results
-------
For every fixed distant-site case, physical reads and allocation counts/bytes
match the direct physical and no-site paths exactly. Adding a plank drops from
96 reads and 2 allocations/2624 bytes to 49 reads and 1 allocation/1312 bytes.
Rejected removal drops from 4 allocations/10464 bytes to 2/10016, and accepted
side removal drops from 3/1760 to 1/1312. Removal reader counts stay at 12 and 63.

Median of the three process medians, microseconds per check:
                               baseline distant   fixed distant   fixed no-site
  put plank                         1.859             0.852           0.778
  remove foundation plank           0.727             0.587           0.519
  remove leaf plank                 1.712             1.232           1.161
  already exists                    0.047             0.111           0.055

The distant-site query adds about 0.07-0.08 us over no-site structural checks.
The already-exists case previously returned before doing structural validation;
it now pays the bounded chunk-occupancy query first. Its measured cost rises by
0.064 us (64 ns), while retaining 2 reads, 0 allocations and 0 allocated bytes.
The query trades this small early-rejection overhead for avoiding duplicate
placement proofs and dependent-array allocation when remote sites are present.
